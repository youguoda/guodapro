# 02 — 取词与粘贴的时序模块

**What to build:** 用户在任意应用中选中文字后按下热键，拾语取得这段文字并显示出来。无论取词成功还是失败，用户原本的剪贴板内容都被完整还原，且这次取词动作不在历史中留下任何条目。

**这是全项目技术风险最高的一张票。** 发出模拟按键之后，没有任何事件告知目标应用已经写完剪贴板，只能轮询加超时。等待过短则取不到，过长则发木。粘贴方向是同一类缺陷（需先将焦点交还原窗口再发送粘贴按键），因此两个方向由同一模块、同一套机制处理。

本票只需把取得的文字显示出来即可验证，不涉及翻译。

## 关键发现

### 用户的手指还按在修饰键上

取词由热键触发，而热键触发的那一刻，**用户的手指仍压着该热键的修饰键**。
若此时直接 `SendInput` 一个 Ctrl+C，目标应用收到的是 Ctrl+Shift+C ——在多数
应用里那是另一个命令。发送前必须先为每个仍被按住的修饰键补发一次抬起。

默认热键特意选了 `Ctrl+Shift+Z`，使这条路径**每次都被走到**，而不是只在某些
配置下才暴露。

### 取词不留痕：既有机制已经够用

目标应用响应 Ctrl+C 时写的剪贴板不是拾语写的，照理会被记成条目。但取词全程
阻塞 UI 线程，两条 `WM_CLIPBOARDUPDATE`（目标写入、我们还原）都滞留在队列中，
待返回后才被处理——而那时**最后一次写入是我们的还原**，`GetClipboardOwner()`
已指向自己，两条都被票 07 建立的自我抑制挡下。无需额外机制。

### 无选区与应用无响应无法区分

站在外面看，两者都只是"剪贴板始终没变"。因此它们共用一个结果
`NothingCaptured`，而不是假装拥有并不具备的确定性。提示语同时点出两种可能。

### 已知限制：只还原文本

若用户剪贴板上原本是图片，目标应用响应 Ctrl+C 的那一刻就已经把它替换掉了——
这项技术**救不回它从未见过的东西**。当前实现保证文本的完整保存与还原，图片
待票 09 落地后重新评估。

## 验证记录

Core 侧 13 项测试，**每一条都同时断言"用户原本的剪贴板被还原"**——这是取词
工具唯一不可原谅的失败。覆盖：及时响应、濒临超时才响应（十次轮询中的第九次）、
始终不响应、轮询不失控、无选区不返回上一次的剪贴板内容、剪贴板变了但内容为空
不算取到、原本为空则还原为空、读失败时不发送任何按键、还原失败要如实上报、
写失败时不按粘贴（否则会粘出错误内容）。

全套 51 项通过。

进程级验证：拾语未运行时 `Ctrl+Shift+Z` 可被外部注册，拾语运行时注册失败，
证明热键确已注册成功，冲突检测路径同时得到验证。

**仍待人工冒烟**：在真实应用里选中文字按热键，确认取到的文字正确、原剪贴板
完好。这需要真实选区，自动化替代不了。
