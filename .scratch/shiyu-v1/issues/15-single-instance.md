# 15 — 单实例保护

**What to build:** 拾语在同一时间只有一个实例在运行。用户重复启动时（双击图标、
开机自启与手动启动撞车、或忘了它已在后台），第二个进程不驻留，而是让用户看到
明确的"已经在运行了"反馈，然后退出。第一个实例毫发无伤。

**这是一张缺陷票，不是新功能**，发现于票 01 完成后的验证过程：一个遗留实例
占着 DLL 导致构建失败，才暴露出根本没有任何单实例约束。

两个实例同时运行会坏在几个地方，而且坏得不明显：

- **两个剪贴板监听**同时记录同一次复制，产生重复条目；更糟的是各自的"与上一条
  相同则刷新时间戳"判断看到的是不同的历史状态，去重逻辑互相打架
- **两个托盘图标**，用户退出其中一个，另一个还在
- **全局热键**（票 02、06、08）只有先启动的那个能注册成功，后启动的会报"热键被
  其他软件占用"——而那个"其他软件"其实是拾语自己，用户没有任何线索能想到这一点
- **保留策略的清理作业**（票 12）被并发执行两次

WAL 能防住数据库文件损坏，但防不住上面这些逻辑层面的错乱。

**排在末位只是因为编号，不代表该最后做。** 它只阻塞于 01，且越早落地，此后每张
票的手工验证就越不容易被幽灵实例污染。建议紧随 01 之后。

**Blocked by:** 01

**Status:** done

- [x] 同一时间只存在一个拾语实例
- [x] 重复启动时，第二个进程不驻留，并让用户**看得见**反馈，而非毫无动静
- [x] 第一个实例的托盘图标、剪贴板监听与已注册的热键，均不受第二次启动影响
- [x] 重复启动的那一次不在历史中留下任何条目
- [x] 前一个实例被强制结束（非正常退出）后，下一次启动能正常运行，不被残留状态
      挡住——这是朴素的锁文件方案最典型的失效方式，需有测试
- [x] 开机自启与用户手动启动几乎同时发生时，不会产生两个实例
- [x] 两个进程几乎同时启动时，恰好有一个存活，不会出现两个都退出的情况

## 验证记录

用互斥量实现：同一会话内只有一个进程能创建它，操作系统在进程消亡时自动释放，
因此崩溃不会留下挡住下次启动的残留锁。第二个实例在**碰任何东西之前**就判断并
退出——先于打开存储、先于注册剪贴板监听，所以它不可能留下痕迹。

作用域取会话级而非全机级：同一台电脑上的两个用户各自跑各自的拾语，历史互不相干，
本就没有争用的必要。

进程级验证全部通过：

| 验收项 | 结果 |
|---|---|
| 首个实例存活 | 是 |
| 第二个实例自行退出 | 是，退出码 0 |
| 第一个实例不受影响 | 是 |
| 同时刻实例总数 | 1 |
| 强制结束后可正常重启（无残留锁） | 是 |
| 两个进程几乎同时启动 | 恰好存活 1 个 |
| 第二次启动不留条目 | 是，历史中恰好 1 条 |

Core 层没有可供单元测试的逻辑——判断全在平台层，且"互斥量在进程被杀后释放"
是操作系统保证，只能在进程级验证。上表即为该验证。

**仍待人工确认**：第二次启动时托盘气泡提示的实际显示。消息通路已验证
（第二个实例广播、运行中的实例接收），但气泡本身的渲染属 UI，只能眼看。
