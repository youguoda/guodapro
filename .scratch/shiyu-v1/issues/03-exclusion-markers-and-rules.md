# 03 — 排除标记与排除规则

**What to build:** 用户从密码管理器复制密码时，该内容不进入历史。用户还能自行配置"不记录"的规则——按来源应用或内容模式——并且开箱就带有一份合理的预设清单，不必从零配置才安全。

项目已决定历史数据**不加密**，因此排除机制是保护敏感内容的唯一防线。

**实现前必须核对 Microsoft 官方剪贴板文档**，确认排除标记的确切格式名称与行为。此前的判断未经一手来源核实，而这一条直接关系到用户的密码是否会被明文写入磁盘。

## 核实结论（对照微软官方文档）

文档：Clipboard Formats — "Cloud Clipboard and Clipboard History Formats"。
共有**三个**注册剪贴板格式，不是一个：

| 格式名 | 语义 |
|---|---|
| `ExcludeClipboardContentFromMonitorProcessing` | 放入**任意**数据即表示：不进历史、不跨设备同步 |
| `CanIncludeInClipboardHistory` | 序列化 `DWORD` = 0 不进历史；= 1 明确要求进历史 |
| `CanUploadToCloudClipboard` | 序列化 `DWORD` = 0 **仅**表示不跨设备同步 |

两点要紧的：

1. **遵守是自愿的。** 文档措辞是应用"可以控制此行为"，Windows 并不强制任何
   剪贴板工具照办。因此拾语遵守它们是本项目自己的决定——而在历史不加密的
   前提下，不遵守不是一个可辩护的选项。
2. **第三个格式刻意不采纳。** 它管的是跨设备同步，而拾语从不同步。把它当作
   "本地也要保密"来解读，会为用户完全有理由期待能找到的内容，在历史里凭空
   挖出看不见也解释不了的洞。

## 预设清单的取舍

预设只列密码管理器，且只按**应用名**匹配。曾考虑从文本本身猜测"这看起来像个
密码"，已否决：两个方向都不可靠，而每一次误判都在历史里留下一个用户既看不见
也想不通的空洞。支付与网银类由标记覆盖——它们会设标记，而其进程名与窗口标题
实在太杂，枚举不过来。

应用名用**包含**匹配而非相等，因为进程名常带版本号与后缀（`1password8`），
而在这件事上漏匹配是代价更高的方向。

## 验证记录

Core 侧 10 条单元测试覆盖标记排除、来源应用规则、内容正则规则、规则增删的
即时生效、预设命中与不误伤，以及**写错的正则排除一切都不排除、而不是排除一切**。

真实 Win32 链路另用一个会真正往剪贴板打标记的工具验证，四种情况全部符合：

| 打的标记 | 结果 |
|---|---|
| 无 | 记录 |
| `ExcludeClipboardContentFromMonitorProcessing` | 不记录 |
| `CanIncludeInClipboardHistory` = 0 | 不记录 |
| `CanIncludeInClipboardHistory` = 1 | 记录 |

用户可编辑规则的界面属票 14；本票交付机制与开箱可用的预设。
