# 07 — 管理窗口：列表与搜索

**What to build:** 用户点击托盘图标，打开完整的**管理窗口**，浏览全部历史条目，并用关键词搜索找回很久以前复制的内容。可在窗口内重新复制任意条目、删除单个条目、按时间段批量删除、一键清空全部历史。

管理窗口服务的是每周数次的"翻检整理"，因此可以大、可以久留、可以有筛选器——与每日数十次的快速粘贴场景截然不同，二者刻意分为两个入口。

历史**绝不整体加载进内存**，一律按需查询。这是"占用内存小"在本模块的具体含义。

## 搜索实现的取舍

**用 `LIKE` 子串扫描，不用 FTS5。** 全文索引的分词器不切中文——"剪贴板历史"
会被索引成单个词元，搜"剪贴板"将一无所获，对一个中文用户的工具而言等于没有。
trigram 分词器能绕开这点，但两字以内的查询（"翻译"这种再常见不过的词）又会落空。

先量后定：5 万条历史下搜索耗时远低于一次击键能掩盖的时长（整套 38 项测试连
播种带断言共 335ms）。既然扫描够快，就不引索引的复杂度。该判断连同理由写在
`EntryStore.Search` 的注释里，将来规模变化时有据可依。

用户查询中的 `%` 与 `_` 会被转义。不转义的话，用户搜一个 `%` 就会静默地
命中整个历史——这条单独有测试。

## 分页与内存

`HistoryBrowser` 承担分页状态机，放在 Core 因而可测：读到哪、还有没有、
新搜索让什么作废。**每一条读取路径都必须带 limit**，历史永远不会被整体载入内存。
删除单条时用 `Forget` 就地剔除，不重读，用户不会被弹回列表顶部。

## 自我抑制

从管理窗口重新复制条目时，拾语会监听到自己的写入。用 `GetClipboardOwner()`
判断剪贴板归属即可精确识别——归属于自己的窗口就是自己写的，跳过不记。重新
复制改为显式 `Touch` 把该条移到最前，这正是用户刚刚表达的偏好。

同一机制票 02 的取词还原也要用。

实例数保持 1，条目正常记录。

修掉一个自己引入的缺陷：搜索框占位文字原用普通属性绑定且无变更通知，用户一
输入占位字不会消失、会与输入内容叠在一起。改为在文本变更时直接设置可见性。
