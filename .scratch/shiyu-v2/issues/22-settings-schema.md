# 22 — 设置即数据

**What to build:** 把设置界面改造成由**一棵数据树**驱动：标签页 → 分区 → 设置项，
每一项声明自己的标识、控件类型、取值路径、关键词、父项与禁用条件。
文案按标识查，图标按标识查。界面本身不硬编码任何一项设置。

分区按**用户意图**组织，不按代码模块——"记录 / 历史 / 动作 / 界面 / 快捷键 / 数据 / 关于"，
而不是"常规 / 高级"。

## 为什么这是整个参照实现里最值得抄的结构

七十多项设置写成数据之后，**三件事是白送的**：

1. 设置内搜索——遍历数据树即可，不必为搜索另写一套索引；
2. 从任意位置深链到某一项——传一个标识就够；
3. 首次引导页复用同一批控件定义——一份数据，三处消费。

写成硬编码界面的话，这三件事要各写一遍，而且会各自腐烂。

## 一个要避开的坑

参照实现把十一项设置声明成了"分段控件"，渲染层却统一渲染成下拉框——
主题切换因此要点两次还看不到选项。**声明了什么就渲染什么**，
渲染层偷懒会让数据层的设计意图白写。

## 实现记录（2026-09-26）

- 三层结构：`SettingsSchema`（Core，纯数据树：页→分区→项，每项声明标识/控件型/
  范围/选项/关键词/父项，文案即标识所查）→ `SettingsBindings`（App，唯一的值层：
  id ↔ AppSettings 读写交换机）→ `SettingsWindow` 渲染器（只认控件形状，不认任何
  一项设置）。新增设置 = 树上一片叶子 + 一个绑定分支，渲染器零改动——票 23 的
  设置搜索与首启引导将直接消费同一棵树。
- 页按意图：记录 / 动作 / 界面 / 快捷键 / 服务 / 数据 / 关于（无"常规/高级"）。
  删除保护重构为"主开关 + 收藏/置顶两个子项"（新增 AppSettings.ProtectEntries
  默认开，三个保护调用点取 主开关 && 子项，行为不变）。
- 分段控件如实渲染（主题三键排开，选中即着色）；数值失焦/回车提交、按范围钳制、
  未提交亮边框；凭据 PasswordBox 永不回显留空即保留；子项随父开关收起。
  备份按钮与版本号也走树声明（Custom/ReadOnly 控件型）。
- 树完整性十一测：id 唯一、父项必为 Toggle 且存在、数值 Min<Max、分段 ≥2 选项、
  关键词齐备、页非空、旧设置面全覆盖、凭据必为 Password、主题必为 Segmented。
- 探针实录（SHIYU_OPEN_SETTINGS=1 直开）：七页齐全、主题三段式、主开关关掉后
  两个子项消失/开启回归、999 输入回车被钳为 20、服务页五个编辑器。
