# 01 — 技术验证：穿透覆盖层与跨窗口连接线

**这是一张验证票，不是功能票。** 交付物是一个结论和一份最小可运行样例，不是可发布的功能。

**What to build:** 一个全屏、透明、置顶、不接受激活的覆盖窗口，上面画一条 2px 贝塞尔曲线，
两端各一个圆点。曲线起点跟随另一个窗口里的某一行，终点连到覆盖层上的一个浮动面板。
**面板可以点击，面板之外的区域鼠标事件必须穿透到下面的应用。**

## 为什么必须先验证

这是整个视觉方向里唯一我们**没有实证**的能力，而它决定了预览体验做成什么样。

已知的难点：`WS_EX_TRANSPARENT` 是**整窗生效**的——设了它整个窗口都穿透，
面板也点不了；不设它整个窗口都挡住下面的应用。参考实现（EcoPaste）用的是
Web 技术栈，浏览器的命中测试天然按元素走，WPF 没有这层免费的东西。

可能的出路有几条（动态切换扩展样式、按区域改命中测试、拆成两个窗口各管一件事），
本票的任务就是把它们试出来，**选一条并写清楚为什么**。

若三条路都不成立，需要给出退化方案——例如放弃连接线、把预览做成贴边面板——
并说明退化后损失了什么。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 覆盖窗口全屏透明、置顶、出现时不夺走前台窗口的焦点与选区
- [ ] 曲线与端点圆点绘制正确，随源行位置变化而重新计算
- [ ] **面板区域可点击，面板之外鼠标事件穿透到下层应用**——这一条是本票的核心
- [ ] 多显示器、不同缩放比例下坐标正确
- [ ] 覆盖层存在期间，下层应用的交互（点击、滚动、输入）不受影响
- [ ] 结论写进票内：选了哪条路、为什么、代价是什么；若不可行则给出退化方案

## Comments

### 进展（2026-09-25）

样例已建在 `spikes/OverlaySpike/`，带 `--selftest` 模式：它不靠肉眼，而是用
`WindowFromPoint` 问 Windows 自己「这一点的点击会落到哪个窗口」，把答案写成报告。

**已确立的结论：**

- **不需要 `WS_EX_TRANSPARENT`。** 票里担心的「整窗生效」问题在这条路上不存在：
  `AllowsTransparency=True` 让窗口成为分层窗口，而分层窗口的命中测试由操作系统
  **按像素 alpha** 完成，且**跨进程有效**。alpha 为 0 的区域天然穿透，不透明区域
  天然可点——一个窗口就够，不必拆成两个，也不必动态切换扩展样式。
- **覆盖层不夺取前台焦点**（多次测量一致）。
- **面板之外穿透到下层应用**：探测点落在模拟的下层窗口上时，Windows 返回的是
  下层窗口而非覆盖层。
- **覆盖层空白处不拦截**：探测点落在曲线区域时，Windows 返回的是屏幕上原有的应用。

**过程中挖出的两条工程结论，对票 17 / 18 直接有用：**

1. **不要把 `SetWindowPos`（物理像素）和 WPF 的坐标变换混用。** 试过用
   `SetWindowPos` 把覆盖层铺满整个虚拟桌面，结果 WPF 的变换仍按它自己记的
   `Left/Top` 计算，`PointToScreen` 与 Windows 的命中测试**各说各话**。
   让 WPF 独占几何、且**覆盖层只覆盖一块屏而非整个虚拟桌面**——预览覆盖层本来
   也只属于源行所在的那块屏——之后坐标系立刻自洽。

2. **分层窗口的命中测试依据的是「已合成到屏幕的画面」，不是布局结果。**
   `UpdateLayout()` 只排布不渲染；面板移动之后、下一帧合成之前，Windows 仍按
   **旧形状**做命中测试。样例里因此出现过「WPF 说面板在这里、Windows 说这里没有
   面板」的矛盾。产品实现中，面板移动后若立刻依赖新位置可点，需要等一帧。

**尚未完成的一条：** 面板位于**正确位置**且已合成之后是否可点。面板停在画布原点时
测得可点（成立），但把它移到正确位置后的那次测量遇上机器锁屏，三个探测点全部返回
锁屏窗口，整轮作废。样例已加入有效性校验，会把这类污染标记为无效而不是当成结论。

**需要：机器解锁后重跑一次自测。**
