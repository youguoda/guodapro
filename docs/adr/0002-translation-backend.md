# ADR-0002：翻译后端的形状与首个实现

- 状态：已接受
- 日期：2026-09-21

## 背景

"反应快"是硬约束；"接入本地 agent"是明确需求。两者表面冲突（本地 LLM 吃数 GB
内存、延迟高），实则不冲突：本地 agent 是**独立服务进程**，应用只是 HTTP 客户端，
其内存不计入应用预算。真正的冲突在**延迟**。

## 决策

1. **翻译后端是一个可插拔接口**，不是写死的调用。它同时是后续特色功能
   （术语解释、整段总结、对历史做归纳）的挂载点。
2. **首个实现复用用户已有的阿里云 MaaS（qwen）凭据**，而非另接专用翻译 API。
   取舍：牺牲延迟与单位成本，换取零注册、单一凭据、单一错误处理路径。
3. **接口是流式的**，从第一版就是。译文逐字呈现，首字到达即开始阅读。
4. **prompt 必须强制"只输出译文"**。通用 LLM 默认会加戏——解释、给多版本、
   把一个词扩成一段。这是 LLM 充当翻译时的头号翻车点，需要测试覆盖。

## 后果

**正面**

- 一个后端同时支撑翻译与特色功能，活动部件最少。
- 流式把 1~2 秒的真实延迟压成 200ms 的**感知**延迟。
- 本地 agent 日后作为第二实现接入，不需要改动调用方。

**负面 / 成本**

- 接口从"给文本、返回译文"变为"给文本、返回流"，错误处理显著复杂：
  流中断怎么办、已显示的半截译文留不留、超时如何界定。
- 单位成本高于专用翻译 API（按 token 计费）。
- 译文质量依赖 prompt 工程，不像专用翻译引擎那样开箱稳定。

## 被推翻的备选

- **专用翻译 API（有道/腾讯/百度）做快路径** — 延迟与短文本质量更优、更便宜，
  但需多管一套凭据与错误处理。用户选择以延迟换活动部件更少。
- **DeepL** — 质量最佳，但国内直连不稳；依赖代理才能工作的快路径与"反应快"矛盾。
- **纯本地 agent** — 隐私与离线最优，但首字延迟不稳定，且强制要求 Ollama 常驻。
- **骨架屏 / 转圈** — 接口更简单，但每次都要干等 1~2 秒，长期使用无法接受。
