## 2. 产品与功能分析

### 2.1 产品哲学（PRODUCT.md 明文）

五条设计原则：手势发生在阅读处；**阅读永不中断**（非激活弹窗）；单词给卡片、段落给流畅翻译；**零配置**（无账号无密钥）；简洁快卡胜过丰富慢卡。"非目标"一节明确拒绝 macOS/Linux/移动端/账号体系，并写有"证据不得虚构：无截图、无证言、无用户研究"——这个文档自觉在开源产品里属于前 1%。

### 2.2 功能清单（代码实证）

- **划词链路**：拖选（≥5px）/双击（自实现 450ms 计时）/三连击句选，全局鼠标钩子；划词后浮**徽章，点击才翻译**（v1.2.2 默认——"未点击不翻译不耗额度"）
- **单词卡**：音标/词性/释义/例句/屈折变化/同义词/所在原句（词典=api.dictionaryapi.dev；原句=UIA TextPattern）
- **句子/段落**：整段翻译 + **逐句对照配对**（sentencePairs）
- **单位货币换算**：译文内联换算（12 ft ≈ 3.66 m），汇率 6h 缓存
- **三引擎**：cloud-baidu / cloud-youdao / google，回退链 + 卡上切引擎/目标语言 + 标注"谁在应答"
- TTS 朗读（SAPI，按语言匹配系统音色）；历史（50–500，重开不重新请求）；忽略进程列表（30 秒点击拾取器）；设置导入导出（"导出不含秘密"）；托盘/自启/单实例
- **README 宣称但源码不存在**：OCR 截图翻译、文档翻译、Ctrl+Enter 回填（v1.5.1–1.5.3 发布说明里描述了，tag 树里没有——见 §7 红旗）

## 3. 技术架构

- **框架**：Tauri 2 + WebView2，前端**零构建**（frontendDist 直指 src/，无 React/Vite——和 TieZ 的 React 19 相反的极端选择，对 384×120 的小卡片是合理的）
- **三窗口**：main（设置/历史 880×690）/ notice（角落提示）/ popup（划词卡，非激活+置顶，代码注释明确 WS_EX_NOACTIVATE 防抢焦点）
- **线程模型**：进程内多线程——鼠标钩子线程→mpsc→手势分类 worker；SAPI 专用 COM 线程；UIA worker；tokio 只开 time feature（几乎纯同步 reqwest）
- **存储**：纯 JSON（settings.json 带 formatVersion/坏文件自动备份；history.json 明文——注释理由"翻译不是秘密"）；无 SQLite
- **凭据**：DPAPI 加密基础设施完整（含"序列化结果不含明文"的测试断言），但**当前构建没有任何服务向用户要密钥**——零密钥是品牌承诺
- **契约治理**：`contract/contract.json` 冻结 38 条 IPC 命令 + 37 个 settings key，契约测试守护

## 4. 翻译模块专章（本报告核心素材）

### 4.1 拓扑：客户端零密钥，凭据全在服务端

```
客户端 ──POST {clientId, text, from, to, vendor}──▶ 代理(CF Worker/腾讯SCF)
                                                      ├─ LLM: 智谱 glm-4-flash（免费档，OpenAI 兼容，非流式）
                                                      ├─ 百度翻译（md5 签名，服务端持有 appId/key）
                                                      └─ 有道智云（SHA-256 v3 签名，服务端持有）
客户端 ──GET──▶ Google 免费公开端点（非官方，伪装 Chrome UA，双 client 回退 + 120s 冷却）
客户端 ──GET──▶ api.dictionaryapi.dev（单词卡增强，8s 超时 best-effort）
```

- 服务端编排：**LLM→百度→有道固定级联**，客户端选的 vendor 只是把谁提到最前；失败级联而非报错
- **客户端没有任何 UI 直接选 LLM**——LLM 是服务端的隐形兜底/主力
- **无 SSE/无流式**：全部一次性 REST；"流式感"靠两阶段加载（翻译先出、词典细节 600ms 预算内补上否则放弃）

### 4.2 LLM Prompt（server/src/llm.js 逐字实证）

System：`You are a careful professional translator.` User 五段：翻译指令（语言 tag 转人名）→"只回 JSON 无代码栅栏"→`{"sourceLang":"<BCP47>","translation":"<译文>"}`→"保留原文换行与标点；专有名词按母语者习惯译；不加注"→原文。temperature=0.2，20s 超时，非流式。**无术语表、无上下文、无 few-shot、无记忆**。解析防御：剥 code fence、缺字段归一错误码。

### 4.3 划词工程细节（含金量最高的部分）

1. WH_MOUSE_LL 独立线程只报原始事件，手势分类在 worker 上（钩子线程保持轻量——与我们票 18 的钩子纪律一致）
2. 自实现双击判定（450ms + 6px slop），三/四连击 250ms 窗口吸收，**拖选永不延迟**（有测试钉死）
3. 取词=模拟 Ctrl+C（提权窗口用 Ctrl+Insert），**RAII 守卫还原剪贴板，且刻意在弹窗显示之后才 drop**（"还原可以等，被复制的应用可能还需要剪贴板"）
4. 过滤链：总开关→每手势开关→最小长度→**须含字母+拒绝路径**（`C:\...`）→源语言白名单→忽略进程表→前台是桌面/shell 时早退（"桌面上 Ctrl+C 只会复制剪贴板里原本的东西"）
5. **回声检测**：译文 resembles 原文时自动换目标语言重试

### 4.4 配额系统（server/，~70KB，MIT 可复用）

按设备 20k 字/天 + 按 IP 30k 字/天 + 全局 30k 字/天 + 单请求 2k 字 + 30 req/min；**上游失败退还已计字符**；IP 只存加盐哈希；配额错误码带剩余量与重置时间；00:00 UTC 重置。已知弱点（作者自己承认）：clientId 仅格式校验——"是配额身份不是鉴权"，可被伪造绕过。

### 4.5 错误处理

客户端回退链（只给用户看第一个错误，全灭固定文案）；Google 专用（429→限流文案、`<html` 响应→BLOCKED、1500ms 快速预算失败→120s 全局冷却）；上游瞬态码（百度 52001/52002/54003、有道 411/412/501）以 [600,1400]ms 退避重试两次；两家错误码全量映射表；语言护栏（不支持的语言组合到不了供应商）+ 各家私有语言码归一（百度 jp/fra/cht）。

## 5. 代码质量与工程实践

**质量面**：注释密度高且写"为什么"（`lib.rs` 的 WS_EX_NOACTIVATE 解释、`Cargo.toml` 解释为何只编 rlib）；模块边界清晰（translate/platform/units/前端 render 纯渲染 + bridge IPC 壳）；可测试性注入设计（server 摆脱 Worker 全局、"时间可注入"、前端 bridge 在纯浏览器降级 mock）；`vitals.rs` 资源泄漏计数（钩子/剪贴板/语音句柄）；选择→卡片延迟埋点（p50 42ms/p95 53ms 写进 README 当预算）。弱点：上游响应用非类型化 `serde_json::Value` 链式 get；CLI 仅 Windows。

**工程面**：CI 六道门禁（版本一致性→前端测试→server 测试→fmt→clippy -D warnings→cargo test --locked），permissions 最小化，并发组自动取消；发布流水线 tag-版本一致性校验 + 三语 release notes 完整性检查（"无 TODO: translate 残留才发"）+ SHA256SUMS。测试规模真实：Rust 214 + 前端 202 + server 74。

## 6. 安全与隐私

- **隐私姿态是加分项**：无遥测无账号不记录选择内容；PRIVACY.md 逐项写清数据流（翻译文本、单词、货币代码、更新检查各自去哪）；IP 加盐哈希；设置目录删了即全清
- **扣分项**：①代理端点无鉴权，知道 URL 的任何人都能消耗作者额度（仅靠配额兜底）；②Google 非官方端点+伪装 UA 属灰色用法（封禁风险作者自己用双 client+冷却缓解）；③默认端点是作者个人腾讯 SCF 单点；④未签名 + updater pubkey PLACEHOLDER（自动更新实际不可用）

## 7. 活跃度与维护风险（含红旗）

- 9 天 59 commits 25 releases 后**自然收尾**（2026-09-25 最后提交），零社区——大概率是"AI 辅助的课程作业级冲刺"，作者是否继续维护未知
- **最大红旗：发布物与公开源码不一致**。v1.5.1–v1.5.3 的 release notes 描述了 OCR 端点/文档翻译/Ctrl+Enter 回填/SignPath 签名，但经 git tree API 核实，**v1.5.1 tag 与 main HEAD 是同一棵树，其中不存在这些功能的任何代码**（无 ocr.rs、无回填命令、contract.json 无对应条目），CHANGELOG 停在 1.4.0。合理解释是私有分支开发、公开仓库滞后镜像。**对借鉴者的含义：1.5.x 无源码可学；对该项目用户的含义：供应链不可复现不可审计。**
- 教训入库：**"release notes 描述的功能必须有对应 tag 源码"应当成为拾语自己的发布守则**（我们的票 28 更新流从 GitHub Releases 拉包，这条守则直接保护我们的用户）。

## 9. 拾语翻译模块可行性建议（本报告落点）

按"价值 × 成本 × 与拾语立场的兼容性"排序，分三档。

### 9.1 【战略级】免费零配置翻译通道（抄架构，不抄代码也行——它是 MIT）

**问题**：拾语新手引导里最重的一步就是填 DeepSeek key；没 key 的用户翻译功能等于不存在。Glossy 证明了另一条路：**密钥留服务端、客户端只发文本+匿名安装 ID、免费档 LLM（智谱 glm-4-flash）兜底、三级日配额防滥用**。

**可行性方案（分两期）**：
- **一期（验证期）**：部署一个 Cloudflare Worker（Glossy 的 server/ ~70KB 是 MIT 参考实现，配额/退款/IP 加盐哈希/错误码全套可对照重写——按拾语纪律用 C#/TS 重写并加测试，不直接拷贝以保持我们的工程一致性），上游先只接智谱 glm-4-flash 免费档。客户端加第三种后端类型 `RelayBackend`（Core 里实现与 `OpenAiCompatibleBackend` 同接口），设置里叫"公共通道（免费额度）"。**额度策略照抄**：设备 2 万字/天、IP 3 万、全局封顶、失败退款、配额错误带剩余量。隐私披露写进设置页与新手引导："翻译的文本会经我们的中转发给模型服务，剪贴板历史本身仍不出机器。"
- **二期（默认化）**：数据验证后把公共通道设为新用户默认（用户 key 变成"高级：自备密钥"）。这一步把拾语翻译的激活率从"填了 key 的人才用"变成"开箱即用"。

**风险与对策**：成本滥用（配额+clientId 不可伪造性的承认上限——Glossy 作者也承认，够用）；隐私叙事（历史不出机器的承诺不破——只有被主动翻译的文本出行，与今天用户 key 模式的数据面相同，披露清楚即可）；服务可用性（CF Worker 免费档 + 我们已有 GitHub Releases 基础设施，零月成本起步）。

### 9.2 【体验级】单词词典卡 + 逐句对照（拾语短板，纯增量）

- **单词卡**：选中文本是单个英文单词时，走 `api.dictionaryapi.dev`（免费、无 key）出词典卡（音标/词性/释义/例句/同义词），**两阶段模式照抄**：翻译先出、词典细节 600ms 预算内补上否则静默放弃。Core 加 `DictionaryCard` 模型 + 可注入的词典端口（保持纯）；App 侧在 PanelWindow 渲染或独立小卡。中文单词走 LLM 词典化 prompt 兜底。
- **逐句对照**：Core 加 `SentenceAlign.Pair(原文, 译文)`（标点切分 + 数量/顺序配对 + 不齐时合并策略——Glossy 的 `merge_meanings` 思路），纯函数可测；PanelWindow 加显示开关。**注意：本地对齐而非让 LLM 输出对齐结构**——本地方案对任何后端（含未来公共通道）都成立，且不破坏我们的流式。
- **TTS 朗读按钮**：译文旁一个 🔊（.NET 里 System.Speech/SAPI 一行起，语音线程按 Glossy 的 COM 单元注意事项做）。语言学习者粘性项，成本半天级。

### 9.3 【交互级】划词徽章模式（复用我们已有的徽标基建）

拾语今天靠热键记忆；Glossy 证明"拖选→光标旁浮小图标→点击才译"的零记忆触发更贴近阅读场景。**我们已经有 BadgeWindow（复制后光标旁徽标）全套基建**，补的是：WH_MOUSE_LL 拖选检测（钩子纪律照 WinVHook：回调只上报、工作在 UI 线程）+ 模拟 Ctrl+C 取词（SelectionCapture 已有 borrow/restore，**采纳 Glossy 的次序细节：还原放面板显示之后**）+ 徽章上多一个"译"按钮。默认关闭、设置可开——不能替用户决定全局鼠标钩子的开销。

### 9.4 【质量级】翻译健壮性包（随 9.1 落地，独立也值）

按 Glossy 的成体系做法补我们的单后端脆弱性：
- **回声检测**：`TranslationEcho.IsEchoish(原文, 译文)` 纯函数（相似度阈值），命中且目标语言未强制时换目标重试——立即可做，不依赖任何新通道
- **回退链**：`TranslationChain`（Core）：有序后端、只展示第一个错误、全灭固定文案——9.1 落地后天然成为"公共通道→用户密钥"的自动降级
- **瞬态退避与错误码映射**：DeepSeek 错误码表（429/503 类瞬态 [600,1400]ms 重试两次；401/余额类直接人话报错）
- **temperature=0.2** 进我们的 `TranslationPrompt` 默认参数（Glossy 实证值，翻译任务的合理低温）
- **语言检测不靠模型回传**：加本地文字系统判别（CJK/西里尔/拉丁码位统计）先验，供回声检测与 UI 显示，避免为拿 sourceLang 破坏流式

### 9.5 【明确不做】（记录理由）

- **Google 非官方端点 + 伪装 UA**：灰色用法，封禁与合规风险，Glossy 自己都要靠冷却硬扛
- **单位货币换算**：与拾语"效率工具"定位弱相关（Glossy 是阅读工具所以合理）；除非用户反馈要
- **剪贴板轮询取词**：Glossy 非 Windows 才轮询；我们事件驱动已在
- **UIA 上下文句**（单词卡"所在句子"）：有价值但成本高（UIA TextPattern 的应用兼容性泥潭），放 backlog 等单词卡跑通后再评估
- **发布物先于源码**：反向教训入库——拾语守则：**release notes 里的每个功能必须能在对应 tag 的源码里指出来源**（直接保护我们票 28 的更新通道可信度）

### 9.6 落地顺序建议

1. **9.4 的回声检测 + temperature + 错误码映射**（纯 Core，一天级，立刻提质）
2. **9.2 单词卡 + 逐句对照 + TTS**（体验短板，一周级）
3. **9.1 一期公共通道**（战略项，含服务端重写与隐私披露，两周级）
4. **9.3 划词徽章**（依赖单词卡成型后的交互判断）
5. 9.1 二期默认化（数据说话后）
