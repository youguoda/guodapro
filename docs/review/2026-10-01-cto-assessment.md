## 0. 结论

**一句话：拾语的工程地基在个人项目里属于上游水平，但它今天还不是一个能交给别人用的产品。**
分发与信任链几乎为零；首次引导默认的翻译路径对目标用户必然失败；还有一个"清空历史却提示数据没动"的数据事故。
**建议冻结新功能约 3 周，按"止血 → 可发布 → 可信 → 打磨"四段推进，之后再发 v1.0。**

三个判断：

1. **架构对，方向对。** Core / Windows / App 三层由编译器强制隔离，673 个单测全部跑在纯逻辑层。
   8 份 ADR、55 张带验收标准的票、3 份竞品调研——这套流程比多数小团队都规范。
   光标旁的非激活浮层、就地键帽、中文排版，是真实存在的差异化。
2. **产品化远远落后于功能。** 没有 CI，从未发布过版本，没有根 README，开机自启指向开发目录里的 Debug 构建。
   自动更新的信任根是一个**没人注册过**的 GitHub 账号。
   首次引导默认选中的"公共通道"既没有部署，所在的 `*.workers.dev` 域名在中国大陆还被 DNS 污染。
3. **瓶颈已经从"写"转到了"验"。** 6 天写出约 2 万行 C#，但 v2 的 40 张票里有 36 张停在"待人工验收"。
   本次评审抓到的问题恰好集中在单测和代理探针都够不到的两类地方：
   **集成缝**（覆盖导入在线程池里改 UI 状态，而唯一的测试传了空回调），
   **视觉正确性**（连接线画进了预览面板、删除钮的危险色没生效、标题栏字形变成豆腐块）。

## 3. 资产：必须保护、不能回退的

1. **编译器强制的分层**：`Shiyu.Core` 是 `net9.0`，不引用 WPF，所以 673 个测试几秒内跑完、可以无头执行。
2. **非激活浮层的工程体系**：三重非激活（`WS_EX_NOACTIVATE`、`ShowActivated=false`、`MA_NOACTIVATE`），
   ZBand 必填参数（没有默认值，静默置顶写出来就编译不过），`PreviewSizing` 先算尺寸再开窗。
3. **就地键帽**：按住 Ctrl 时，数字键帽直接盖住来源图标，零布局位移；提示和按键处理读同一张 `BarKeys` 表，永远不会提示错键。
4. **中文排版**：正文 18 DIP、行高 1.7，按整数行截断，卡片高度可预测。
5. **隐私的设计意图**：历史只在本机；服务端不记录正文；有排除标记和预设排除清单；同步目录有警告。
6. **两段式更新应用**：先放进暂存区，由第二个进程替换，替换前先备份，失败回滚。机制是对的，缺的只是信任根（见 P0-1）。
7. **决策可追溯**：ADR 写清了"被推翻的备选"，例如 ADR 0007 写明 SQLCipher + DPAPI 是"第一顺位的回头选项"。
8. **票的验收写法**：每张票都有可观察的验收条目。这是让代理开发可控的关键。

## 4. 发布阻断项（P0）

### P0-1 自动更新的信任根指向一个无人注册的账号

- **现象**：`UpdateChannel.Default` 是 `("guodapro", "shiyu", "shiyu-win-x64.zip")`（`src/Shiyu.Core/UpdateFeed.cs:132`），
  而仓库实际位于 `youguoda/guodapro`（现已改名为 `youguoda/shiyu`）。2026-10-01 实测 GitHub API：`users/guodapro` 和 `repos/guodapro/shiyu` 都返回 404。
  这意味着**任何人都可以注册这个账号**，再建一个 `shiyu` 仓库发布 v99。
- **为什么危险**：
  - 启动 5 秒后会静默检查一次更新，发现"新版本"就弹托盘通知（`App.xaml.cs:226-260`）。
  - 客户端**不验签**。校验和文件来自同一个发布，取不到时直接放行（`UpdateService.cs:120-137`，有意的 fail-open）。
  - 应用随开机自启，替换后的程序就成了常驻进程。
- **缓解因素**：安装需要用户点击；目前没有外部用户。
- **另一面**：在被抢注之前，自动更新功能实际上一直是死的（永远 404，而且静默）。
- **修法**：
  - 立刻把默认通道改到真实仓库（S）。
  - 首次公开发布前加入签名校验（M）：minisign 或 Ed25519，公钥内置在程序里，清单和安装包都要验签；去掉 fail-open。
  - 生产构建移除 `SHIYU_UPDATE_API` 环境变量覆盖，只在调试构建里保留（S）。

### P0-2 覆盖导入会清空历史，然后提示"现有数据没有被动过"

- **证据链**（已逐行复核）：
  1. 导入在线程池执行（`BackupUi.cs:302`）。
  2. `ReadInto` 先 `store.ClearAll()`，以独立事务立即提交（`BackupArchive.cs:346-349`）。
  3. 接着回放设置（`BackupArchive.cs:368-372`）。回调是 `App.RestoreSettingsFromBackup`，原样传入，没有切回 UI 线程（`BackupUi.cs:80-84`，`App.xaml.cs:391-407`）。
  4. 该回调切换主题，会遍历已附着的窗口读 `IsLoaded`（`Backdrop.cs:69`）。这是依赖属性读取，跨线程必抛异常；而发起导入的设置窗一定是开着的。
  5. 异常被 `BackupUi.cs:311-315` 的 `catch (Exception)` 接住，弹出"备份操作失败了，现有数据没有被动过。"
- **实际后果**：历史和分组已经被清空并提交；设置文件已经被覆盖；一条都没导入进来；原图目录变成无引用的孤儿文件。
- **触发条件**：覆盖导入，并且备份里含设置。首次启动就会写设置文件，所以本应用导出的备份几乎都含设置。
- **为什么测试没发现**：唯一的覆盖导入测试传的是空回调 `applySettings: _ => { }`（`tests/Shiyu.Core.Tests/BackupTests.cs:76`），App 侧的接线从来没被测过。
- **修法**：
  - 回调切回 UI 线程执行（S）。
  - 覆盖导入改成"先导入临时库，成功后再替换"（M）。
  - 失败提示不再断言"数据未动"（S）。
  - 补一个用真实回调的集成测试（S）。

### P0-3 新用户的第一次翻译必然失败

- 首次引导对没配密钥的用户**预选公共通道**（`OnboardingWindow.cs:330-335`，这是票 36 的有意设计）。
- 但公共通道的默认端点 `https://shiyu-relay.workers.dev`（`RelayBackend.cs:50`）有三个问题：
  - **从未部署**（票 36 待验收）。
  - **形态是占位符**：Workers 的默认域名是"脚本名.账号子域.workers.dev"。
  - **在中国大陆整域被 DNS 污染**。2026-10-01 实测：本地解析到 Facebook 的地址段 `2a03:2880::/32`；
    AliDNS 对该域名返回 Facebook 段，对 `workers.dev` 返回 Twitter 段；TLS 握手失败。
    就算部署了，大陆用户也连不上。
- **同类问题**：管理窗的批量翻译和 Agent 动作永远走自备密钥（`App.xaml.cs:631`）。选了公共通道的用户在这里会 100% 失败，而批量翻译是静默计数失败。
- **影响**：这个产品的主要受众是中文用户，他们的首个核心体验就是一条错误。
- **修法**（需要你拍板，见 §7-1）：
  - v1 引导改为"自备密钥优先 + 国内可达的服务商预设 + 一键测试连接"（S–M）。
  - 公共通道推迟到二期，绑定自定义域名并完成防滥用后再开（M–L）。
  - 管理窗的模型来源与面板保持一致（S）。

### P0-4 交付链为零

- 没有 CI（`.github/workflows` 不存在），所以 673 个测试只在作者本机跑。
- 从未发布过任何版本；没有根 README；没有安装位置。
- 开机自启直接指向开发目录里的 Debug 构建产物。后果有三：
  - 只要应用开着，构建就会因 DLL 被锁而失败（已经实际造成过一次"改了看不到"）。
  - 一次失败的构建或 `git clean`，就会让每天在用的应用坏掉或消失。
  - 用户手里的版本和仓库的任何提交都对不上号。
- **修法**：
  - GitHub Actions：Windows 跑构建和 673 个单测，Linux 跑 37 个服务端测试（S）。
  - 打 tag 自动产出 zip、签名和校验和（M）。
  - 安装到 `%LOCALAPPDATA%\Programs\Shiyu`，自启指向安装位置（S）。
  - 补根 README：是什么、截图、安装、隐私承诺（S）。

## 6. 战略判断与建议

### 6.1 冻结功能 3 周，按闸门推进

| 阶段 | 时长 | 出口闸门（全部可观察） |
|---|---|---|
| 0 止血 | 2–3 天 | P0-1、P0-2 修复并有测试；全局异常处理和本地日志上线（日志绝不含正文）；复制去重、设置互相覆盖打上补丁 |
| 1 可发布 | 约 1 周 | CI 为绿；打 tag 能产出带签名的 zip；安装位置与自启修正；README 上线；按引导默认路径，首次翻译成功率实测 100% |
| 2 可信 | 1–1.5 周 | SQLite 加锁；钩子迁到专用线程；排除名单统一闸口；设置单一写入口；服务端加固；待验收票从 36 降到 10 以下 |
| 3 打磨 | 1–2 周 | 设计令牌落地；删除隐式 `TextBlock` 样式；浮层家族统一；UI 报告里的 P0/P1 清零（这一阶段可以与少量功能并行） |

### 6.2 翻译通道：v1 走"自备密钥优先"

公共中转是一项**运营承诺**，不是一个功能：要付模型调用费，要防滥用，还要保证大陆可达。
`workers.dev` 在大陆不可达，所以至少要绑自定义域名。可选的方向有：Cloudflare 自定义域名（大陆多数地区可用，但稳定性一般）；
香港区域的云函数（免备案）；大陆区域（域名需要 ICP 备案）。三者在成本和合规上差异很大，需要单独评估。

DeepSeek 一类国内可达的模型已经很便宜。v1 更好的路径是：**引导里预设国内可达的服务商、粘贴密钥、一键测试连接**。
等有真实用户数据之后，再决定中转值不值得运营——这也正是票 36 原本写的"二期默认化另行开票"。

### 6.3 把验证变成系统，而不是人工

- **给验收债设 WIP 上限**：待人工验收的票超过 5 张，就不开新票。
- **探针进仓库**：`tools/probes/`，统一走 `SHIYU_DATA_DIR` 隔离数据。本次评审已证明逐像素取样可以抓到真实缺陷，把它固化成截图断言。
- **集成缝要有测试**：把 App 层里的决策逻辑抽进 Core（候选清单见《优化报告》§5）。规则是：回调参数不允许只用空实现测试。
- **CI 是前提**：没有 CI，以上都会退化成"作者记得跑"。

### 6.4 信任模型补齐三处

1. **更新链**：签名校验，没有任何 fail-open。
2. **密钥**：只给密钥本身上 DPAPI（`CurrentUser` 范围，约 20 行代码）。这不推翻 ADR 0007——它接受的是历史库明文，不涉及密钥；备份默认不带密钥。
3. **排除名单是唯一闸口**：所有取词和剪贴板路径（历史记录、划词徽标、借出还原、Agent 动作）都过同一个 `ExclusionPolicy` 判定点，并用一个测试覆盖所有入口。

### 6.5 界面：先建系统，再改界面

设计师的结论是"底层 7 分、表层 3 分"，根因集中在七条（R1–R7），尤其是隐式 `TextBlock` 样式和 Aero2 默认模板。
先把令牌、组件和状态矩阵落地，再逐个界面套用；否则每个界面都要重修一次。详见 UI 报告。
