## 1. 阶段 0：止血（2–3 天）

**出口闸门**：O-01 到 O-07 全部合入，并且都有测试；覆盖导入用真实回调的测试为绿。

### O-01 · P0 · S — 更新通道的信任根

- **问题**：默认通道是 `guodapro/shiyu`（`Shiyu.Core/UpdateFeed.cs:132`）。这个 GitHub 账号**不存在**，任何人都可以注册它，然后发布一个"新版本"。详见判断报告 P0-1。
- **做法**：今天就二选一：
  - 把默认通道改到真实仓库 `youguoda/shiyu`；
  - 或者立即注册 `guodapro` 账号或组织，占住这个命名空间（如果你打算用这个名字发布）。

  签名校验放在 O-10 做。
- **验收**：
  - 单测断言默认通道指向的仓库存在：CI 对 GitHub API 做一次 `repos/<owner>/<repo>` 冒烟，返回 200。
  - 在本机从托盘手动"检查更新"，得到的是"已是最新"或真实的发布，而不是静默无反应。

### O-02 · P0 · S — 覆盖导入：设置回放与失败文案

- **问题**：
  - `ReadInto` 先 `ClearAll` 并提交（`Shiyu.Core/BackupArchive.cs:346-349`），再在线程池上调用 `RestoreSettingsFromBackup`（`:368-372`，`Shiyu.App/BackupUi.cs:302`）。
  - 后者碰到 UI 对象必然抛异常（`Shiyu.App/Backdrop.cs:69` 读 `IsLoaded`）。
  - 异常被吞后弹出"现有数据没有被动过"（`BackupUi.cs:311-315`），而实际上历史已经被清空。
- **做法**：
  - `BackupArchive.Import` 不再接收回调，改为在结果里返回设置 JSON。`BackupUi` 等 `await` 回到 UI 线程后再应用。
  - 失败文案按阶段区分：清空之前失败，才能说"数据未动"；清空之后失败，要说清"已清空、导入未完成"，并提供"从备份重试"。
- **验收**：
  - 新单测：`Import` 不调用任何回调，返回值里带设置 JSON，条目数正确。
  - 新单测：在第 N 条处注入异常，抛出的 `BackupException` 能区分"已清空"和"未清空"。
  - 人工：设置窗开着时做一次覆盖导入，主题、热键、窄条置顶全部按备份生效，没有错误弹窗。

### O-03 · P0 · M — 覆盖导入的原子性

- **问题**：即使修好 O-02，"先清空、再逐条导入"如果中途失败，仍会留下半个库。
- **做法**：二选一：
  - 把清空、建组、导入全部放进**一个事务**（SQLite 处理大事务没有问题）。原图先写到临时目录，事务提交后再移动过去。
  - 或者先导入到一个临时库文件，成功后关库、替换文件、重开。

  推荐前者，改动面小。
- **验收**：单测在第 N 条处注入失败后，库里的条目数、分组数与导入前**完全一致**，原图目录没有多出孤儿文件。

### O-04 · P0 · S–M — 首次翻译路径

- **问题**：引导对没配密钥的新用户预选公共通道（`Shiyu.App/OnboardingWindow.cs:330-335`）。但这条通道必然失败，原因有三：
  - 端点从未部署；
  - 端点的形态是占位符（`Shiyu.Core/RelayBackend.cs:50`）；
  - `*.workers.dev` 在中国大陆被 DNS 污染。

  详见判断报告 P0-3。
- **做法**（取决于判断报告 §7 第 1 项的决定，下面按推荐方案写）：
  1. 公共通道的选项在端点真正部署、并通过可达性检查之前**不显示**，由一个编译期或配置开关控制。
  2. 引导的翻译步改为"自备密钥"：预设几家国内可达、OpenAI 兼容的服务商（选中即自动填好地址和模型），并提供**测试连接**按钮；允许"稍后配置"。
  3. 没配置翻译服务时，划词或热键翻译显示一张"去配置翻译服务"的引导卡，**不显示异常文本**。
- **验收**：
  - 用全新的 `SHIYU_DATA_DIR` 按默认选项走完引导，复制一个英文单词，点徽标。面板只会显示两种结果之一：译文，或配置引导卡。**任何情况下都不出现异常文本。**
  - 测试连接对"密钥错误""地址错误""超时"三种情况，分别给出不同的人话结果。

### O-05 · P0 · S — 全局异常处理与本地日志

- **问题**：
  - 没有 `DispatcherUnhandledException`、`TaskScheduler.UnobservedTaskException`、`AppDomain.UnhandledException` 处理器。
  - `catch (Exception)` 共 53 处，其中 45 处静默。
  - 4 个 `async void` 没有保护：`Shiyu.App/App.xaml.cs:547`（`ShowPanel`）、`LibraryWindow.xaml.cs:698` 与 `:795`、`PanelWindow.xaml.cs:414`。更新窗的"安装"点击（`UpdateWindow.cs:90`）也一样。
  - `AppSettings.Save` 没有 catch（`Shiyu.Core/AppSettings.cs:278-291`）：设置文件被占用时，点一下置顶钉就会让进程退出。
  - 对一个托盘常驻的记录工具来说，崩溃就等于**静默停止记录**：用户以为历史还在记，其实已经没有了。
- **做法**：
  - 装上三个全局处理器，统一写入 `%LOCALAPPDATA%\Shiyu\logs\shiyu-yyyyMMdd.log`，滚动保留 7 天，单个文件不超过 1 MB。
  - **日志只记事件名、异常类型和堆栈，绝不记剪贴板内容、译文或密钥。** 用一个专门的 `Log` 门面强制这一点：参数只接受枚举和异常，不接受任意的字符串插值。
  - UI 线程上的非致命异常：记日志，托盘提示一次，继续运行。
  - 4 个 `async void` 和 `Save` 都包上 try，并接入同一个日志门面。
  - `OnExit` 里把"归还划词借走的剪贴板"挪到最前面（`App.xaml.cs:666-692`），免得前面的步骤一抛异常就跳过了它。
  - 关于页加"打开日志目录"。
- **验收**：
  - 调试构建里有一个隐藏命令，会在 `DispatcherTimer.Tick` 中抛异常。触发后进程存活，日志里多一行，托盘提示一次。
  - CI 中加一条静态检查：`Log` 调用的参数里不出现 `Text`、`Translation`、`ApiKey` 一类字段名。

### O-06 · P1 · S — 复制去重修复

- **问题**：`MostRecent()` 的实现是 `Recent(limit: 1)`（`Shiyu.Core/EntryStore.cs:577`），而 `Recent` 先按 `pinned DESC` 排序（`:880`）。剪贴板管线用它来判断"是不是同一次复制的重复通知"（`Shiyu.Core/ClipboardPipeline.cs:95, 134-140`）。
  **只要置顶过任意一条**，比较的就变成"最新的置顶条目"，不再是刚复制的那条。后果有三：
  - 一次复制会触发多次通知的应用，每复制一次落下 2 条以上的重复记录；
  - 连续复制同一段文字，每次都新增一条；
  - 复制的内容恰好等于最新置顶条目时，`Touch` 会改掉置顶条目的时间戳。
- **做法**：`MostRecent` 改用独立的 `ORDER BY created_at DESC, id DESC LIMIT 1`，正好命中现有的 `idx_entries_created_at` 索引。
- **验收**：新单测：先置顶一条，再连续追加两次相同文本，库里只多出一条记录。（现有测试中没有任何一处在有置顶时调用 `MostRecent`。）

### O-07 · P1 · S — 设置互相覆盖：最小补丁

- **问题**：每个写设置的地方，都是用自己手里那份**完整快照**整份写回，所以最后保存的一方获胜。
  - 设置窗的快照在开窗时取得，此后从不刷新（`Shiyu.App/SettingsWindow.xaml.cs:22, 43`）；保存时以它为底，把**所有**项重放一遍（`:867-888`）。
  - 窄条的置顶钉（`BarWindow.xaml.cs:140-146`）和引导窗（`OnboardingWindow.cs:433-439`）也各自持有一份旧快照。

  已经推导出的复现路径：
  - **S1** 打开设置窗 → 在窄条上点置顶钉 → 回到设置窗点保存：窄条当场恢复置顶。
  - **S2（最严重）** 首次运行时，引导窗还开着，用户试着唤出了窄条 → 完成引导 → 之后任何时候点一下置顶钉：窄条手里那份"引导前"的快照被整份写回，**引导里填的密钥、后端、热键、排除规则全部丢失**。下次启动时历史已非空，引导不会再出现。
  - **S3** 导入备份后，在同一个设置窗里点保存：恢复的设置被回滚。
  - **S4** 在设置窗里"重新运行引导"，引导和设置窗会互相覆盖。
- **做法**（最小补丁；根治在 O-20）：
  - 设置窗记录每项的初值，保存时只把**改过的**项应用到**最新的**设置上。`_apply` 改成接收一个 `Func<AppSettings, AppSettings>`，由 App 在当前值上求值。
  - 窄条的置顶钉只上报一个布尔值，由 App 执行 `_settings with { BarAlwaysOnTop = … }`。
  - 引导完成和导入完成之后，关闭或重建设置窗。
- **验收**：S1–S4 各写成一个人工步骤加入 `docs/manual-test-v3.md`，全部通过。O-20 落地后改为 Core 单测。

### O-08 · P0 · S — 持续集成

- **做法**：GitHub Actions 建两个 job：
  - `windows-latest`：`dotnet build -c Release`，然后 `dotnet test`；
  - `ubuntu-latest`：在 `server/` 下执行 `npm ci && npm test`。

  主分支开启保护，CI 为绿才能合并。
- **验收**：任意 PR 上都能看到两个绿色检查；故意弄坏一个测试的 PR 无法合并。

### O-09 · P1 · M — 发布流水线

- **做法**：推送 `v*` tag 时触发：
  - 构建 `win-x64` 包。推荐 self-contained，用户不用另装运行时，代价是包体大几十 MB。也可以选 framework-dependent，包更小，但要求用户先装好 .NET 9 桌面运行时。
  - 生成 zip、SHA-256 和签名（见 O-10），并创建 GitHub Release；Release 正文由本版本合入的票自动汇总。
  - 程序集版本号来自 tag（`-p:Version=`），关于页和更新比较都读这个版本号。
- **验收**：推一个 `v0.9.0-rc1` tag，十分钟内出现一个 Release，里面有 zip、`.sha256` 和 `.sig`；下载解压后可以直接运行，关于页显示 0.9.0。

### O-10 · P0 · M — 更新验签

- **做法**：
  - 签名用 .NET 内置的 `ECDsa`（P-256），**零新依赖**，符合这个项目"只有一个 NuGet 包"的克制。公钥内置在程序里，私钥只存在发布机或 CI 的加密变量里。
  - 客户端先验签，再解压。
  - **去掉"校验和取不到就放行"的 fail-open**（`Shiyu.App/UpdateService.cs:120-137`）。
  - 生产构建去掉 `SHIYU_UPDATE_API` 环境变量覆盖，只在 Debug 下保留。
  - 顺手修两处：
    - 更新窗做成单例（`App.xaml.cs:214-217`）。现在每次点"检查更新"都会新开一个窗口，两个窗口会互相删除对方暂存区里的文件。
    - `InstallAsync` 包上 try。
- **验收**：
  - 三个单测：签名正确的通过；篡改 zip 1 个字节的被拒；缺签名的被拒。
  - 端到端：用本地 HTTP 冒充发布源，提供一个篡改过的包。更新窗明确报"签名不符，已拒绝安装"，暂存区被清空。

### O-11 · P0 · S — 安装位置与开机自启

- **问题**：开机自启直接指向开发目录里的 Debug 构建产物。
  - 应用开着时构建会被锁（已经实际造成过一次"改了却看不到"）；
  - 一次失败的构建或一次 `git clean`，就能让每天在用的应用坏掉或消失。
- **做法**：
  - Debug 构建**永远不写** HKCU Run。
  - Release 第一次运行时，提示安装到 `%LOCALAPPDATA%\Programs\Shiyu`，或者解压即用、自启写当前路径。
  - 开发时用独立的 `SHIYU_DATA_DIR` 跑 Debug；日常使用 Release。
- **验收**：
  - 启动 Debug 构建前后，HKCU Run 的值不变（用探针读取比较）。
  - Release 从安装目录启动后，自启项指向安装目录。

### O-12 · P1 · S — 根 README

  - 一句话定位；

### O-13 · P2 · S — 版本与变更记录

- **做法**：
  - `CHANGELOG.md` 按版本列出合入的票。
  - 关于页加"复制版本信息"：版本号、系统版本、DPI，不含任何个人数据，方便用户反馈问题。
- **验收**：v0.9.0 的 Release 正文与 CHANGELOG 一致。

### O-14 · P1 · S — 管理窗的模型来源与面板一致

- **问题**：管理窗的批量翻译和 Agent 动作，永远用自备密钥构建后端（`App.xaml.cs:631`）。没配密钥的用户点下去 100% 失败，其中批量翻译只是静默地记一笔失败数。
- **做法**：
  - 批量翻译和面板共用同一个后端工厂（`BuildTranslationBackend`）。
  - Agent 动作需要通用对话模型，而公共通道不提供，所以没配密钥时这些按钮**禁用**，tooltip 写"需要自备密钥 · 去设置"。
- **验收**：
  - 没配密钥时，Agent 按钮显示为禁用，并带说明。
  - 批量翻译结束时报告"成功 n / 失败 m"，失败原因可见。

**出口闸门**：

### O-15 · P1 · S — SQLite 线程安全

- **问题**：`EntryStore` 只有一个 `SqliteConnection`，没有任何同步（`Shiyu.Core/EntryStore.cs:12, 27-32`）。图片入库、保留清理、备份导入导出这三条路径跑在线程池上，会和 UI 线程并发访问它。可能的后果：
  - 命令被并入别人的事务；
  - 跨事务边界时抛异常（没有全局处理器，进程就直接崩溃）；
  - `last_insert_rowid()` 错配，导致标签挂到错误的条目上（`EntryGroups.cs:56-58`、`EntryBackup.cs:48`）。
- **做法**：
  - `EntryStore` 内加一个 `private readonly object _gate`，每个 public 方法体用 `lock (_gate)` 包起来。`Monitor` 可重入，内部方法互相调用没有问题；事务都是在单个方法内开启并提交的。
  - `CreateGroup`、`ImportEntry` 改用 `INSERT … RETURNING id`。
- **验收**：压力测试：4 个线程对同一个 store 混合执行 1,000 次读写（含 `ImportEntry` 事务），零异常，行 id 全部正确。

### O-16 · P1 · M — 低级钩子迁到专用线程

- **问题**：
  - Win+V 接管和划词这两个低级键鼠钩子，都装在 UI 线程上（`App.xaml.cs:699-737`）。
  - 取词时，同一线程会用 `Thread.Sleep` 轮询，最长 600 ms（`Shiyu.Core/SelectionCapture.cs:208-230`，`Shiyu.Windows/WindowsCapturePlatform.cs:79`）。
  - 微软文档写明：钩子回调超时，系统会**静默移除**这个钩子，应用无从得知。

  三个后果：
  - 开着划词时，每次拖动窗口、拖滚动条都会走一遍取词。期间整个系统的鼠标会卡住，划词徽标还可能无声失效。
  - 开着 Win+V 接管时，取词注入的 Ctrl+C 要经过自己线程上的钩子而迟到。剪贴板已经还原之后，它才把选区复制进来，覆盖掉用户的剪贴板。
  - 装钩失败（`SetWindowsHookExW` 返回 0）不检查，被系统移除后也没有任何信号；设置里仍然显示"已开启"。
- **做法**：
  - 两个钩子迁到一条专用后台线程：线程里调用 `SetWindowsHookEx`，并运行自己的 `GetMessage` 循环；事件经 `Dispatcher.BeginInvoke` 投给 UI 线程。这正是微软文档推荐的形态，`WinVFilter` 和 `SelectionDrag` 都不用改。
  - 取词等待改为不阻塞消息泵：Core 里的 `Wait` 端口改成 `ValueTask WaitAsync`。
  - 检查装钩的返回值，失败时上报；托盘菜单提供"重新接管"。
- **验收**：
  - 开启划词，连续拖动窗口标题栏 20 次：光标没有可感知的停顿，划词徽标仍然有效。
  - 开启 Win+V 接管后按划词热键：用户原来的剪贴板在 1 秒后依然完好（探针读取剪贴板序列号和内容做比较）。

### O-17 · P1 · S–M — 排除名单统一闸口

- **问题**：ADR 0007 写明"排除规则成为唯一防线"，但有几处入口绕过了它：
  - 划词徽标路径（`App.xaml.cs:749-783`）不查排除名单，会向密码管理器模拟 Ctrl+C；
  - 剪贴板借出与还原、Agent 动作，也都没有复核排除名单。
- **做法**：
  - 在 Core 里建立唯一的判定点 `CaptureGate.Allows(source)`。所有"读取别人内容"的入口都先经过它：历史记录、划词徽标、热键取词、Agent 动作。
  - 划词路径要在**模拟 Ctrl+C 之前**，就按前台进程做判定。
  - 热键取词是显式请求，仍然允许；但前台进程在排除名单里时，先提示一次。
- **验收**：
  - 每个入口都有单测。
  - 探针：在排除名单里的进程中拖选文字后，剪贴板序列号（`GetClipboardSequenceNumber`）不变，也没有徽标出现。

### O-18 · P1 · S — 密钥保护

- **问题**：`BackendApiKey` 以明文存在设置文件里。"不加密导出"的备份会带上整份设置（`BackupUi.cs:39-50`），密钥也就跟着出去了。
- **做法**：
  - 只对密钥使用 DPAPI（`ProtectedData`，`CurrentUser` 范围）；首次加载时把旧的明文自动迁移过去。
  - 备份**默认不含密钥**；只有"加密导出"时才可以勾选包含。
  - ADR 0007 接受的是"历史库明文"，并不涉及密钥，所以不需要推翻它。另写一份 ADR 记录这次取舍即可。
- **验收**：
  - 设置文件里搜不到密钥原文；
  - 不加密导出的备份解压后，也搜不到密钥原文；
  - 升级之后，原有的翻译功能照常可用。

### O-19 · P1 · S–M — 服务端加固（部署前必做）

- **问题**：
  - `to` 字段不限长度，直接插进提示词（`server/src/prompt.ts:24`），而且不计入额度（只计 `text`，`server/src/handler.ts:48`）。这既是提示词注入，也是额度绕过。
  - 全局每日 20 万字的上限，可以被少量 IP 耗尽，构成对所有用户的拒绝服务。
  - IPv6 没有按 /64 聚合。
  - KV 的额度预留不是原子操作。
  - `IP_HASH_SALT` 没设置时会回退到默认值。
- **做法**：
  - `to`、`from` 改为语言代码白名单。
  - 按"实际送进模型的字符数"计费。
  - IPv6 按 /64 聚合。
  - 增加每个 IP 的突发限速。
  - 额度计数改用 Durable Object 或其他原子计数。
  - 缺少 `IP_HASH_SALT` 时拒绝启动（fail closed）。
- **验收**：vitest 每条各写一例：
  - 超长 `to` 返回 400；
  - 不在白名单里的语言被拒；
  - 同一个 IPv6 /64 共享额度；
  - 缺盐时健康检查失败。

### O-20 · P1 · M — 设置只有一个写入口（根治 O-07）

- **做法**：
  - 在 Core 里放一个 `SettingsStore { Current; Update(Func<AppSettings, AppSettings>); event Changed }`。所有写入都是"在最新值上做增量"，所有窗口订阅 `Changed` 刷新。
  - 顺带解决 audit A2 记下的几处：
    - 启动引导的回调只生效了一半：热键、主题、窄条本次会话不刷新（`App.xaml.cs:195-206`）。
    - 面板的译文语言不跟随设置变化（`PanelWindow.xaml.cs:72-73`）。
    - 加载失败时回落默认值，并**立即覆盖原文件**（`AppSettings.cs:241-272` 加 `App.xaml.cs:110-113`）。改为先把原文件改名为 `settings.json.bad-<时间>`，再写默认值。
    - "只在内存里生效"的 `SHIYU_RELAY_URL` 被写进了文件（`App.xaml.cs:99-113`）。
- **验收**：
  - Core 单测：两个调用方交错修改不同字段，最终两处修改都保留。
  - 再一条单测：加载一份损坏的文件，原文件被改名保留，没有被覆盖。

### O-21 · P1 · S–M — 设置窗的保存模型

- **问题**：设置窗用的是显式"保存"，可关闭窗口时又静默丢弃改动（`SettingsWindow.xaml.cs:960`）。
- **做法**：按 UI 报告 §6.3，改成**即改即生效**（Win11 惯例）：
  - 开关、分段、下拉，改完立即生效；
  - 数值、文本在按 Enter 或失焦时，合法才生效；
  - 数据位置、导入备份、自备密钥这三类保留显式操作。
- **验收**：UIA 探针做两件事：
  - 切换主题，不点任何按钮直接关窗，再打开：主题仍是新值。
  - 输入一个非法数值：旧值保持不变，卡片内显示错误。

### O-22 · P1 · S / M — 存储性能

- **问题**（静态估算，未实测）：
  - **每次启动都重扫全部普通文本**（`EntryStore.cs:204, 258-312`）。普通文本的子类型存的是 NULL，而回填的选择条件恰好就是 `sub_type IS NULL`，所以每次都会被重新选中。10 万条时，估计启动多花 0.5–2 秒，冷盘时更久。这段时间托盘图标和剪贴板监听都还不存在，期间的复制会漏记。
  - **所有列表查询都是全表扫描再排序。** 排序的首列 `pinned` 没有索引（`:602, 635, 746, 880`）。缩略图和 HTML/RTF 存在行内，并且排在 `pinned`、`note` 之前，读这两列要先走完大字段的溢出页。混合内容 10 万条时，每次搜索、每次复制估计让 UI 卡顿 0.3–1 秒以上。
  - 搜索用 `LIKE '%x%'`；快速条每按一个键就查一次，没有去抖（`QuickBarWindow.xaml.cs:85-90`）。
- **做法**：
  - **S**：
    - 建索引 `(pinned DESC, created_at DESC, id DESC)`；
    - 无子类型时写一个哨兵值；
    - `Count()` 加缓存；
    - 快速条加去抖。
  - **M**：
    - `thumbnail`、`html`、`rtf` 拆到附表；
    - 搜索改用 SQLite FTS5 的 `trigram` 分词器（保留子串匹配语义，支持中文）；
    - 分页改用 keyset，替代 `OFFSET`。
- **验收**：用占位数据生成 10 万条混合库，脚本测量以下三项（结果记录在票里）：
  - 启动到托盘出现 < 1 秒；
  - 窄条一次搜索 < 100 ms；
  - 一次复制的入库 < 20 ms。

### O-23 · P2 · S — 共享 HttpClient 与超时策略

- **问题**：
  - 每次翻译、每次查词都新建一个 `HttpClient`，每次都要多一轮 DNS + TCP + TLS 握手（约 100–300 ms），直接加在首字延迟上，还吃掉 600 ms 免费词典预算的一大块。
  - `OpenAiCompatibleBackend` 的 30 秒 `CancelAfter` 覆盖整个流，长文本会在 30 秒处被截断。
- **做法**：
  - 进程级共享一个 `HttpClient`（`SocketsHttpHandler`，`PooledConnectionLifetime` 设为 5 分钟），通过各个类**现有的**可选构造参数注入。
  - 超时拆成两段："首字节超时"（如 15 秒）和"相邻数据块之间的空闲超时"（如 20 秒），不再限制流的总时长。
- **验收**：
  - 连续翻译两次，第二次的首字时间明显下降（本地计时；日志里只记毫秒数）。
  - 一段 2,000 字的流式翻译，不再在 30 秒处被截断。

### O-24 · P1 · M — 静默 catch 治理

- **做法**：45 处静默 catch 逐一归类处理：

  - **预期外的**：记日志（见 O-05）。
  - **影响到用户的失败**：在界面上告诉用户。

  CI 增加一条检查：`catch (Exception)` 的块内，必须有 `Log.` 调用或 `// expected:` 注释。
- **验收**：
  - 这条检查在 CI 中为绿。
  - 重点几处都有日志或界面提示：保留清理、更新检查的 404、词典回退链、批量翻译的失败计数。

## 6. 架构演进方向（不急，但要先定下方向）

1. **设置是一个可观察的存储，不再是到处传递的快照**（O-20）。各模块订阅变更，自己决定怎么应用；`App` 不再逐个调用 `_bar?.ApplySettings`、`_pipeline.RecordImages = …`。
2. **取词与排除是 Core 里的一个模块**（O-17）。所有入口共用一个判定点，并有一份审计日志；日志只记"入口 + 结论"，不记内容。
3. **平台层收口**（O-39）。`Shiyu.Windows` 是唯一接触 Win32 的地方。DWM、DPI、窗口定位、低级钩子线程都下沉到这里，"按目标显示器取 DPI"也就只需要写一次。
4. **诊断不出机器。** 不引入任何云端遥测或崩溃上报，这与"历史不出机器"的承诺一致。只用本地日志，加上用户主动导出的"诊断包"（日志加版本信息，不含内容）。
5. **翻译后端是一个可替换的端口。** 面板、词典、批量翻译、Agent 动作都从同一个工厂取后端，并声明各自需要的能力（流式翻译，或通用对话）。能力不满足时，界面禁用并说明原因，而不是等到运行时才失败。
6. **存储为规模设计**（O-22）。列表只读窄表，大字段放附表；搜索走 FTS5 trigram；变更通过事件广播，不靠轮询。

## 8. 不建议做的事

- **补齐验证之前，不要继续加功能。** v2 已经有 40 张票，其中 36 张还没验收。
- **不要把公共中转当作 v1 的默认路径。** 它是一项运营承诺：要花钱、要防滥用、要保证大陆可达。
- **不要继续在分层窗口上叠"材质"。** 先做非分层的 Mica spike（UI 报告 R7）。
- **不要引入云端遥测或崩溃上报。** 这违背"历史不出机器"的承诺；本地日志加用户主动导出就够了。
- **现在不要做整库加密。** ADR 0007 已经权衡过，并把它列为"第一顺位的回头选项"。先把密钥和备份保护好。
- **不要一个界面一个界面地修视觉。** 先修 UI 根因 R1 和 R2，否则同一类缺陷会在别处复发——从票 30 到票 33，这已经发生过一次。
- **不要在 UI 线程上做任何可能阻塞的事。** 低级钩子也在这条线程上，UI 线程一卡，就是整个系统的键鼠一起卡。
